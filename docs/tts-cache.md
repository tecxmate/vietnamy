# TTS Bucket Cache

## Why

Every Vietnamese audio clip used to be regenerated by Azure or Google Translate on every request. That created two scaling risks:

1. **Google rate-limiting** — the unofficial Translate TTS endpoint blocks IPs that send too much traffic, taking down audio for *every* user at once.
2. **Latency + bandwidth** — Zeabur had to proxy the audio bytes through every time, adding ~300–800 ms and consuming egress.

The fix: generated audio is cached in a public Supabase Storage bucket fronted by Cloudflare. After the first generation, every subsequent request is a 302 redirect from `/api/tts` to the CDN URL. The audio bytes never re-enter Zeabur.

## Architecture

```
Browser ── GET /api/tts?text=...&voice=...
            │
            ▼
       Zeabur Express
       (server.js)
            │
   ┌────────┴────────┐
   │                 │
HEAD bucket      bucket miss
 200 OK?             │
   │                 ▼
   ▼          Azure / Google TTS
 302 redirect       │
   │           upload to bucket
   │           (fire-and-forget)
   │                │
   ▼                ▼
Cloudflare      respond inline
 → Supabase     (Cache-Control: 1 day)
   Storage
```

Object key format: `<voice>/<sha1(voice|lang|text)>.<ext>` where `ext` is `wav` for Azure voices and `mp3` for Google. The hash includes the voice so the same Vietnamese sentence can have separate north / south / google entries.

## Files

| File | Role |
| --- | --- |
| `server/server.js` | `/api/tts` handler — checks bucket via HEAD, redirects on hit, generates + uploads + serves inline on miss. Helpers: `ttsCacheKey`, `ttsPublicUrl`, `ttsCacheHas`, `ttsCachePut`. |
| `scripts/prebuild-tts.mjs` | One-off warm-up. Walks `src/data/` for known Vietnamese keys (`vi`, `vi_text`, `target_vi`, `answer_vi`, `source_text_vi`, `template_vi`, `audio_text`, `vietnamese`), dedupes, and POSTs each (text, voice) pair to `/api/tts`. |
| `README.md` § "TTS Bucket Cache" | User-facing setup quickstart. |

## Setup

1. **Supabase Dashboard → Storage**: create bucket named `tts-cache`, set **Public**.
2. **Zeabur env vars** (or `server/.env` locally):
   ```
   SUPABASE_URL=https://<project-ref>.supabase.co
   SUPABASE_SERVICE_ROLE_KEY=<service-role-key>
   TTS_BUCKET=tts-cache   # optional, defaults to tts-cache
   ```
   Service-role key (not anon) is required because uploads write to the bucket.
3. Redeploy. Verify with `curl -I "https://<host>/api/tts?text=xin%20ch%C3%A0o&voice=azure-north&lang=vi"`:
   - `X-TTS-Cache: miss` → cache enabled, file just uploaded.
   - Call again → `302` with `location:` pointing at the bucket.
   - `X-TTS-Cache: disabled` → env vars not picked up by the runtime.

## Warming the cache

After setup, run the pre-gen script once so users never wait for cold generation on baked-in content:

```bash
# Default: both Azure voices, all data files
node scripts/prebuild-tts.mjs --server=https://<host>

# Sanity-check scope first
node scripts/prebuild-tts.mjs --dry-run

# Limit voices
node scripts/prebuild-tts.mjs --voices=azure-north --concurrency=3
```

Reference run (2026-05-23): 6,787 unique strings × 2 voices = 13,574 requests, ~40 min wall time at 5.7 req/s, 99.9% success rate. ~250 MB in the bucket.

The script is **idempotent** — a second run skips already-cached strings (logged as `hit=N`). Safe to re-run any time new curriculum content lands.

## Operational notes

- **First-render cost stays inside Azure free tier** (500K chars/month). After warm-up, baked-in content costs $0. Only user-typed dictionary lookups and brand-new curriculum strings incur new Azure spend.
- **Cloudflare cache headers** on the served file come back as `cache-control: no-cache` from Supabase Storage (their default, ignores the `Cache-Control` header passed at upload). The browser still benefits because the URL is stable per `(voice, text)` — repeated playbacks reuse the same response. Investigating switching to `cacheControl` upload metadata or moving to R2 would improve this further but is not blocking.
- **Failures during warm-up** (~0.1% in the reference run) are transient Azure timeouts. They self-heal on first user request, which then caches.
- **Cache invalidation**: there is none. The hash includes the full text, so editing a sentence creates a new key automatically. Old keys remain orphaned until manually deleted via the Supabase Storage UI. If this grows large, add a cleanup script that diffs bucket keys against the live data set.

## Failure modes

| Symptom | Likely cause | Fix |
| --- | --- | --- |
| `X-TTS-Cache: disabled` | `SUPABASE_URL` or `SUPABASE_SERVICE_ROLE_KEY` not set on the server | Add env vars in Zeabur, redeploy. |
| Always `miss`, never `hit` | Bucket exists but is private | Toggle bucket to Public in Supabase UI. The HEAD probe needs unauthenticated read. |
| `502 TTS fetch failed` | Upstream Azure / Google failure | Server falls back from Azure to Google automatically; if both fail, returns 502. Not cached, retried on next request. |
| Pre-gen script reports many `fail=` | Server overload or upstream throttling | Lower `--concurrency`. Re-run; only failed strings retry. |

## Scaling outlook

With the cache warm:

- **Zeabur** sees ~1 KB redirect per TTS request instead of 8–80 KB audio. Bandwidth bottleneck removed.
- **Concurrent capacity** is now bound by SQLite dictionary queries (thousands of QPS easily) rather than TTS.
- **CDN** (Cloudflare via Supabase) absorbs the audio traffic. Effectively unlimited concurrency for cached content.

Estimated capacity on a single small Zeabur container after warm-up: **~1000+ concurrent active users**. The next bottleneck would be Supabase Storage egress quotas (free tier: 5 GB/month) — at ~25 KB per clip and ~50 clips per active session, that supports roughly 4,000 sessions/month before needing to upgrade Supabase or migrate the bucket to Cloudflare R2.

# TTS Bucket Cache

## Why

Every Vietnamese audio clip used to be regenerated by Azure or Google Translate on every request. That created two scaling risks:

1. **Google rate-limiting** — the unofficial Translate TTS endpoint blocks IPs that send too much traffic, taking down audio for *every* user at once.
2. **Latency + bandwidth** — Zeabur had to proxy the audio bytes through every time, adding ~300–800 ms and consuming egress.

The fix: generated audio is cached in a public Supabase Storage bucket fronted by Cloudflare. After the first generation, every subsequent request is a 302 redirect from `/api/tts` to the CDN URL. The audio bytes never re-enter Zeabur.

A second concern emerged as we iterated on voice quality (clarity boost, loudness normalization, prosody). Each tweak invalidated the whole cache because the post-processed WAV was the only thing stored — regenerating ~17K strings from Azure costs real money and burns through the free tier. The bucket now uses a **two-tier cache** that separates raw Azure output from post-processed WAVs, so iteration is nearly free.

## Architecture

```
Browser ── GET /api/tts?text=...&voice=...&ck=<version>
            │
            ▼
       Zeabur Express (server.js)
            │
   ┌────────┴──────────────────────┐
   │ 1. Derived hit?               │
   │    HEAD <version>/<voice>/... │
   │    .wav                       │
   └────────┬──────────────────────┘
            │ 302 ──► Cloudflare ──► Supabase Storage
            │
            ▼ (miss)
   ┌─────────────────────────────────┐
   │ 2. Source hit?                  │
   │    HEAD source/<voice>/<sha1>   │
   │    .pcm                         │
   └────────┬────────────────────────┘
            │ download → re-derive WAV locally
            │ → upload derived → serve inline
            │
            ▼ (miss)
   ┌─────────────────────────────────┐
   │ 3. Call Azure TTS               │
   │    save raw PCM → source/...    │
   │    apply clarity + loudness     │
   │    wrap as WAV → derived/...    │
   │    serve inline                 │
   └─────────────────────────────────┘
```

### Two-tier object layout

```
tts-cache/
├── source/                              # unversioned, never invalidated
│   ├── azure-north/<sha1>.pcm           # raw trimmed PCM from Azure
│   └── azure-south/<sha1>.pcm
└── <TTS_CACHE_VERSION>/                 # e.g. v9-nam-minh-lower
    ├── azure-north/<sha1>.wav           # post-processed WAV
    └── azure-south/<sha1>.wav
```

- **Source key**: `source/<voice>/sha1(voice|lang|text).pcm` — raw Azure output, no clarity, no normalization, no WAV wrapper. Persists forever.
- **Derived key**: `<TTS_CACHE_VERSION>/<voice>/sha1(voice|lang|text).<wav|mp3>` — post-processed final audio. Lives under a version prefix so we can invalidate it by bumping `TTS_CACHE_VERSION` without touching source.
- **Google TTS path** (used only as last-resort fallback) bypasses post-processing and is cached only at the derived tier as `.mp3`.

The version prefix is the lever for voice-quality iteration. Bumping `TTS_CACHE_VERSION='v10-foo'` and redeploying means:

- Every request becomes a derived miss.
- Server falls through to source check → source hit → re-derives WAV locally with the new clarity/loudness parameters → uploads under `v10-foo/`.
- **Zero Azure calls** (after the one-time source backfill, see below).
- First user request per string pays ~100 ms of CPU for the re-derive; subsequent requests are 302 hits at `v10-foo/`.

## Setup

1. **Supabase Dashboard → Storage**: create bucket named `tts-cache`, set **Public**.
2. **Zeabur env vars** (or `server/.env` locally):
   ```
   SUPABASE_URL=https://<project-ref>.supabase.co
   SUPABASE_SERVICE_ROLE_KEY=<service-role-key>
   AZURE_SPEECH_KEY=<key>
   AZURE_SPEECH_REGION=<region>      # e.g. eastasia
   TTS_BUCKET=tts-cache               # optional, default 'tts-cache'
   TTS_CACHE_VERSION=v9-nam-minh-lower  # optional, default 'v9-nam-minh-lower'
   ```

   Service-role key (not anon) is required because uploads write to the bucket.
3. **Azure Speech pricing tier**: in Azure Portal → Speech resource → **Pricing tier**, choose **S0 (Standard)** for production. F0 (Free) caps at 500K characters/month and returns 429 once exhausted — no automatic fallback to paid. The S0 rate is ~$16 per 1M characters; the $200 free Azure credit absorbs many years of organic usage.
4. Redeploy. Verify with `curl -I "https://<host>/api/tts?text=xin%20ch%C3%A0o&voice=azure-north&lang=vi"`:
   - `X-TTS-Cache: miss` → cache enabled, file just uploaded.
   - Call again → `302` with `location:` pointing at the bucket.
   - `X-TTS-Cache: hit-source` → source-tier hit, server re-derived locally without Azure.
   - `X-TTS-Cache: disabled` → env vars not picked up by the runtime.

## Warming the cache

After setup, run the pre-gen script once so users never wait for cold generation on baked-in content:

```bash
# Default: both Azure voices, all data files
node scripts/prebuild-tts.mjs --server=https://<host>

# Sanity-check scope first
node scripts/prebuild-tts.mjs --dry-run

# Limit voices
node scripts/prebuild-tts.mjs --voices=azure-north --concurrency=3

# Also pre-cache the top-N most frequent dictionary words
node scripts/prebuild-tts.mjs --server=https://<host> --dict=3000
```

The `--dict=N` flag queries `server/databases/vn_en_dictionary_high.db` for the top-N Vietnamese words by subtitle frequency and adds them to the warm-up set. Useful for covering dictionary lookups so users never wait on common words.

The script is **idempotent** — a second run skips already-cached strings (logged as `hit=N`). Safe to re-run any time new curriculum content lands.

### Iterating on voice quality (clarity, loudness, prosody)

When you tweak parameters in `server.js` (`addPcm16MonoClarity` amount, `normalizePcm16MonoLoudness` target RMS, SSML prosody attributes, etc.), the cached derived WAVs become stale. To roll out new audio:

1. Bump `TTS_CACHE_VERSION` to a new string, e.g. `v10-clarity-bump`. Set it in Zeabur env vars and redeploy.
2. Optionally pre-warm by running `prebuild-tts.mjs` again — it will see all derived files as missing and re-derive each via the source tier (no Azure calls if source is populated; see backfill below).
3. Delete the old `<previous-version>/` folder from Supabase Storage to reclaim space.

If source PCM is populated for every string, this entire cycle costs **zero Azure characters**. The trade-off is a small CPU spike on the Zeabur server during the first request per string (the local re-derive is ~50-100 ms).

### Backfilling source PCM (one-time)

The two-tier code shipped in commit `91608cf` (2026-05-24). Before that, derived WAVs were the only thing stored — there's no source PCM for any of the ~17K strings cached prior. To make them benefit from the new flow:

```bash
node scripts/backfill-tts-source.mjs --server=https://vietnamy.tecxmate.com --concurrency=4
```

The script:

1. Walks every Vietnamese string the app uses (same key pattern as `prebuild-tts.mjs`, plus top dictionary words).
2. HEADs `source/<voice>/<sha1>.pcm` for each.
3. For misses, calls `/api/tts?ck=migrate-source&...` which forces a fresh Azure call. The server saves both `source/<voice>/<sha1>.pcm` (unversioned, permanent) and a throwaway `migrate-source/<voice>/<sha1>.wav` derived file.
4. After the run, **delete the `migrate-source/` folder** in the Supabase Storage UI — it's a byproduct, only the `source/` tier matters going forward.

Cost: ~$3 on S0 (about 90K characters × $16/1M for ~17K strings × 2 voices). Run it once after deploying the two-tier code. Future voice-quality iterations are free.

## Operational notes

- **Azure usage**: combined warm-up runs on 2026-05-24 consumed **~410K synthesized characters** and crossed the 500K/month F0 free tier shortly after. Speech resource is now on **S0 (Standard)**, drawing from the $200 free Azure credit at ~$16/1M characters. The free quota resets monthly; after the cache is warm, only brand-new strings (new curriculum, user-typed dictionary lookups) consume new characters.
- **Watch the meter at** Azure Portal → Speech resource (`VNME-Asia` in this project) → Monitoring → **Metrics** → metric: *Synthesized Characters*, aggregation: *Sum*. The Activity Log panel will look empty — it only tracks resource-management events, not API calls.
- **Cost after free tier** is roughly **$16 per 1M characters** (Neural TTS S0). To put it in perspective: 1,000 brand-new strings per day for a month is ~150K chars, ~$2.40. The cache makes that one-time per string forever.
- **Cloudflare cache headers** on the served file come back as `cache-control: no-cache` from Supabase Storage (their default, ignores the `Cache-Control` header passed at upload). The browser still benefits because the URL is stable per `(voice, text, version)` — repeated playbacks reuse the same response. Investigating switching to `cacheControl` upload metadata or moving to R2 would improve this further but is not blocking.
- **Failures during warm-up** (~0.1% in the first run, 0% in subsequent runs) are transient Azure timeouts. They self-heal on first user request, which then caches.
- **Bucket size**: as of 2026-05-24 after all migrations and cleanup, **~1.4 GB total** across `source/` (~700 MB) and `v9-processed/` (~560 MB). All legacy folders have been deleted. Free tier limit is 1 GB — this is the trigger for the R2 migration tracked in [issue #17](https://github.com/tecxmate/vietnamy/issues/17).
- **Cache invalidation**: bumping `TTS_CACHE_VERSION` invalidates derived WAVs only. The hash on every key includes the full text, so editing a sentence creates a new key automatically; the obsolete one remains until manually deleted. Source PCM only changes if the Azure model changes (rare) — usually you never want to touch the `source/` tier.
- **Backups**: `scripts/backup-tts.mjs` downloads the entire bucket to a local folder (`tts-backup/`, gitignored). Run periodically and store the folder somewhere durable (private repo, external drive, second cloud) so audio survives Supabase project loss.

## Pronunciation Assessment

A related but separate endpoint `POST /api/pronunciation?text=<reference>` accepts a 16 kHz mono WAV body and proxies to Azure Speech's **Pronunciation Assessment** REST API. Returns accuracy / fluency / completeness / pronunciation scores 0–100, plus a per-word breakdown (each word includes its own accuracy + an `errorType` of `None`, `Mispronunciation`, `Omission`, or `Insertion`).

Two surfaces consume it:

1. **`speak_sentence` exercises in `LessonGame.jsx`** — records via `src/utils/recordPCM.js`, uploads, grades the lesson by pronunciation score (≥ 70 → correct). Renders a coloured chip strip showing per-word accuracy so users see *which* syllables they got wrong. Browser `webkitSpeechRecognition` runs in parallel as a fallback transcript source; if Azure is down, the transcript is graded by the existing fuzzy text match (no tone awareness, but the app stays usable).
2. **Tone Trainer** (`src/pages/Practice/ToneTrainer.jsx`) — dedicated minimal-pair drill where the user is shown a target word with a specific tone (e.g. `mả`) plus all same-base tone variants (`ma · má · mà · mả · mã · mạ`). Each round is a single-word reference, scored by Azure. Critical because browser STT transcribes `mã` and `má` to the same text — Azure's phoneme-level scoring is the only way to detect tone errors objectively.

Cost: Azure free tier includes **5 hours/month of audio**. Beyond that, ~$1/hour of speech sent. A typical user practicing 10 min/day fits inside the free tier indefinitely; the $200 credit covers ~200 paid hours on top.

| Re-derive returns 502 with source-tier hit     | Local post-processing threw (likely buffer length issue)                                               | Check`server.js` post-processing helpers; if a bug, the safe rollback is reverting `TTS_CACHE_VERSION` to the last known good value.           |

## Scaling outlook

With the cache warm:

- **Zeabur** sees ~1 KB redirect per TTS request instead of 8–80 KB audio. Bandwidth bottleneck removed.
- **Concurrent capacity** is now bound by SQLite dictionary queries (thousands of QPS easily) rather than TTS.
- **CDN** (Cloudflare via Supabase) absorbs the audio traffic. Effectively unlimited concurrency for cached content.
- **Voice iteration cost** is bound by CPU on the Zeabur server (re-derives) — no per-iteration Azure spend after the source backfill.

## Future improvements

- **Migrate to Cloudflare R2** ([issue #17](https://github.com/tecxmate/vietnamy/issues/17)): free egress, free 10 GB storage. The bucket is already at ~1.4 GB so Supabase Pro ($25/mo) or R2 migration is the next decision. R2 is the obvious winner long-term.
- **Fix Supabase upload Cache-Control**: figure out the right header / metadata syntax so files come back with `cache-control: public, max-age=31536000, immutable` instead of `no-cache`. Currently re-played audio still costs a 304 round-trip to the CDN even though the URL is stable. May become moot after R2 migration.
- **Daily home-PC mirror**: cron job on a home server that lists the bucket and downloads new objects nightly. Disaster recovery if both the cloud provider and our backup repo are lost. Different from `scripts/backup-tts.mjs` (which only mirrors files the app references) — we want a full-bucket mirror.
- **Source-tier compression**: raw 24 kHz mono 16-bit PCM is ~48 KB/sec. Could compress to FLAC (~50% size) before upload. Trade-off is server CPU vs. storage cost; not worth it until the bucket grows much larger.
- **Per-string audit endpoint**: GET `/api/tts/info?text=...&voice=...` returns whether derived exists, whether source exists, and key URLs. Useful for debugging "why am I seeing a miss?"

The script would walk every folder (source/, v9-processed/, future versions), HEAD-check what's
already local, download only the new ones. After the first full sync (~1.5 GB), nightly deltas are
minutes.
